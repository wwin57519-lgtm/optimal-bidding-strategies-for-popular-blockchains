# Solana 新币开盘首买与最优竞价策略

已知 mint、排除项目方捆绑首买的执行方案

机制论文 v2.1  |  2026年10月29日  |  主网案例、参数与预算决策

**核心结论**

争第一笔，应联合优化“最早有效到达、实际执行路径、优先费与 tip、CU 预算”。推荐以预构建交易、双触发发送、路径定向竞价和防重复买入组成执行方案；固定 tip、固定分成或某个 bot 名称，都不能单独确定首买排名。

## 摘要

本文研究已知 mint、排除项目方预留首买后的独立竞争。联合优化预构建、最早有效到达、路径费用和成功 CU。修订版加入可复核主网案例，给出 gas、tip、收款账户、预发送时间及频率的具体选择规则和数值演示。案例能核验执行顺序与费用，不能还原私有发包时刻、bundle 归属或证明固定参数最优；文中严格区分观察值与待验证配置。

关键词：Solana；Pump；首笔买入；优先费；tip；计算单元；多路径发送

## 1 研究目标与适用范围

前提是提前知道代币 mint 地址，项目方的创建交易不包含初始买入，也不以原子 bundle 预定首买。目标定义为：目标曲线或池在规范链上开放后，第一笔成功买入属于自己。这里的“第一笔”按目标交易的实际执行顺序判定；它不同于最先获得接口回执、最先看到 processed，或仅进入首个区块。

在可接受总费用 B 内，最大化 P（目标首买属于自己）

总费用包括成功交易费、所有已上链失败尝试费、实际支付的 tip 及协议费用；部署和数据订阅另列。若没有费用约束，公开规则也不能推出唯一、有限的最优出价。本文只优化首买概率；净利润最高是另一个目标。

**“今天”的证据范围**

查阅日为 2026-10-29。官网确认 Alpenglow 已于 10 月 21 日所在 epoch 上线；200ms slot 与约 150ms 目标终局性是两个概念，执行和费用规则未因该升级而改变。[11] 本文核验官方资料，未探测特定 leader、个人接入权限或实时路由；文档能力不等于当日逐路径实测。

## 2 先确定路径，再分配费用

Solana 没有一个统一竞价入口，能够把所有买单按“付出的 SOL 总额”全局重排。原生调度、传统 Jito Block Engine 与 BAM/DBI 的竞争逻辑不同；执行者应辨认交易最后进入哪套排序流程。[1][3][4]

| 实际路径 | 排序或付款依据 | 竞价含义 |
| --- | --- | --- |
| 原生调度 / 普通转发 | 调度器比较验证者费用收入与估计资源成本；普通 RPC 本身不是独立的链上 tip 接收者。 | 需要足够原生优先费；不能认为高 Jito tip 自动替代原生调度。 |
| 传统 Jito bundle | 冲突账户进入相关竞价，考虑 tip / 请求 CU，选择资源约束下收益较高的组合。 | 提高有效 tip/CU；仅有 tip 总额最大仍不构成首买保证。 |
| BAM / DBI | 官方描述为（优先费 + Jito tip）/ 请求 CU；DBI 直接接入需白名单。 | 同时评估总费用效率、到达时间、接入权限和实际可用性。 |
| Sender Max | 服务商说明采用多路径发送和按 tip 优先的缓冲；另要求原生优先费。 | Sender tip 与验证者优先费都需配置；服务商优先队列不保证全网第一。 |

资料：[1][3][4][5]。费用只影响尚可竞争的位置。传统 sendTransaction 的 70/30 示例不能直接套用到 BAM；“sendBundle 只看 tip”也只适用于相应竞价路径。传统 50ms 竞价描述同样不能作为所有当前路径的固定计时参数。

## 2.1 tip 不必向所有通道重复支付

直接提交 Jito 时，按官方接口选一个 tip 账户即可。Sender Max 文档说明其接收 Sender tip 并处理下游路径 tip，无需逐个附加 Jito 付款。[3][5] 自行接入其他发送商时，应逐一核对其要求，不存在适用于所有服务的通用收款账户。

**一次广播与一次付款**

同一笔成功交易包含 A、B 两笔 tip 转账，就会支付两笔。同一签名向多个兼容入口广播，一般只会在规范链结算一次；改变费用、收款人或 blockhash 后重新签名，则形成不同交易，可能分别执行。买单与 tip 应位于同一笔交易，并配置共享的一次性买入限制。

## 2.2 路由状态属于执行参数

BAM 曾公告升级维护期间回退到传统 Block Engine，并暂停 DBI、MPP。[10] 这是维护安排，不是截至今天全部恢复的证明。应按实际可用路径报价；接入白名单、入口接收和目标 leader 支持分别核验。因路由失效而落后，提高费用未必能补救。

## 3 参数设置：成功计算量、竞争档位与支出上限

以下公式适用于 legacy/v0。设 L 为请求 CU 上限，c 为每 CU 的 micro-lamports 单价，P 为优先费总额（SOL）：[1]

P = ceil(L × c / 1,000,000) / 1,000,000,000

CU 是计算量单位，L 是交易最多允许消耗的计算量，不是金额或发送频率。legacy/v0 单笔上限为 1,400,000 CU。[2] L 太低会超限，固定 c 时虚高 L 会增加优先费，也可能降低按请求 CU 计算的竞价效率。[1][3][4]

| 参数 | 建议起点 | 必须核对 |
| --- | --- | --- |
| CU 上限 L | 完整成功买单的计算量上界加约 10% 余量。[2] | 覆盖代币账户创建、买入、tip 与一次性保护；不是 Pump 通用固定值。 |
| 优先费 P | 按实际可写账户估算；以高竞争档起测，另设单次及累计费用上限。 | VeryHigh 不是 95% 首买成功率；新 mint 无样本时参考同类开盘。 |
| tip T | 按有效路径报价；在预算内为首发选好愿意实际支付的档位。 | 最低准入 tip 不是热门首买报价；全网 tip 分位也不是目标币清算价。 |
| 发送次数 N | 以真实限流、有效窗口和失败费用决定。 | 发送次数不等于上链次数；独立签名可能分别买入和扣费。 |

费用估算应输入完整交易或对应可写账户。工程上可将账户定向 VeryHigh 作为首发的起测候选；它是带余量的尾部报价，并非对手最高出价或 95% 首买保证。新 mint 没有自己的历史样本，应保留同类开盘对照；VeryHigh、UnsafeMax 都可能受极端样本影响。[6]

**尚未创建时如何测 CU**

对不存在的 mint 模拟，往往在真正买入前就失败。这种 unitsConsumed 不能用于成功买单的 CU 上限。应在匹配程序版本和账户分支的测试状态中验证，或用同类成功交易预估并留余量；验证与估价应尽量在触发前完成。

## 3.1 新格式与预算约束

v1 交易通过消息配置直接设置优先费和 CU 限额；旧 ComputeBudget 配置指令不按 legacy/v0 方式生效。[1][2] 解析器、签名与发送商均须支持所用格式，不能只替换费用字段。

若一次事件最多允许 N 笔独立尝试落链，且通过共享保护保证至多一次买入成功，可按保守边界预留：N ×（单笔基础费上限 + 单笔优先费上限）+ 单次成功 tip 上限 + 协议费用 ≤ B。买入本金、可退租金和订阅成本分别列账。

## 4 争取第一笔的执行流程

提前准备 → 双触发 → 路径定向竞价 → 链上核验

预构建：提前解析可确定的曲线地址、quote mint、token program 和费用配置。未知字段从创建消息补齐；仅知道 mint 不保证所有账户都已确定。验证完整买单，缓存模板，临近刷新 blockhash；首发使用预先选好的竞争档位。[8]

双触发：创建时间可预测时，把限流内的小窗口预发送作为增强候选，同时监听最早创建信号。时间不明确时以事件触发为主。过早的普通买单可能执行失败；单独买入的 bundle 也可能因模拟时账户不存在而被拒绝。预发送不是链上挂单，其增益与失败费用必须实测。[3][4]

早信号：Helius 文档区分 leader 执行后信号与 BAM 承诺执行信号；后者结果可能未知，不能当作创建成功。覆盖非全网连续，同一签名还可能来自两个源。工程上按来源解码并去重，保留较晚但覆盖更完整的流。已承诺执行的买单不能靠后来加价插队。[7][13]

低延迟发送：提前预热连接，比较部署区域到信号源、发送入口及执行路径的整体延迟。可以将 Sender Max 与 Jito 直投作为对照；DBI 仅在已获接入且运行正常时加入。通道数量本身不是速度指标；频率应遵守服务限流。[3][4][5]

成交约束：买入、必要状态检查和 tip 放在同一交易。独立交易版本共享一次性买入凭据，首次成功后其他版本回滚，减少重复买入；原生失败手续费仍可能发生。最高支出或最低输出限制决定可接受成交价。[8][9]

**“只买一次”不等于“只买第一笔”**

一次性凭据只能限制自己的成交次数。检查价格或储备，也不必然证明历史上没人买过。若目标程序没有可靠计数或不可伪造的首买条件，就不能宣称具有绝对首买保护；本方案只争取更高的首买概率。

## 4.1 定时开盘的额外条件

必须读取目标池实际的链上 timestamp、slot 或状态门槛，并核对提前交易权限。Meteora Alpha Vault 可在公开开盘前的保护窗口买入；此时目标应定义为“第一笔公开买单”，不能称全历史第一笔。[14] 网页倒计时仅用于准备；不同池的报价与账户模板分别验证。

## 4.2 Alpenglow 之后，怎样正确争与验

截至查阅日，官方将 Votor 标注为主网已上线；Rotor 属于尚未排期的后续阶段。约 150ms 是目标终局性，200ms 是另一项升级后的 slot 时间；二者都不是“我的买单多久能排第一”的承诺。费用与 SVM 执行规则保持原有口径。[11]

| 变化 | 对狙击程序的直接影响 |
| --- | --- |
| 更快最终确认 | 抢买触发使用早信号；事后用规范链结果确认是否成交和首买。最终确认快，不代表可以重排已决定的交易。 |
| 同 slot 的候选 bank | 在同一连接内按 (slot, bank_id) 分开缓冲，保留最终被确认的候选，丢弃废弃分支。 |
| 多家数据源合并 | bank_id 是节点本地计数，不能跨源直接相等连接。封口后按非空 blockhash 对齐；尚无 blockhash 时保留来源隔离。 |

资料：[11]。早信号只用于争取时间；最终首买统计以规范链的创建/开放事件和相关买入顺序为准，不能把不同分支的事件拼成一个开盘。

## 4.3 本文给出的最佳工程选型

| 已知条件 | 推荐选型及费用方向 |
| --- | --- |
| 知道 mint，创建时间不明确 | 预构建 + 最早创建信号 + 已验证低延迟路径。减少触发后的查询和组单；不承诺盲目预发送有增益。 |
| 知道链上开盘门槛 | 在上述方案上比较“受控预发送 + 事件触发”。预先确定费用与限流参数，并统计落链失败成本。 |
| 首买价值高、接受高 tip | 首发使用已选竞争档位；tip 与成交及一次性保护在同笔交易。保持路径所需原生优先费，并单列累计失败费。 |

**最优不是一个通用百分比**

传统 Jito 的 tip/CU、BAM 的总费用/CU、Sender 的服务队列与原生调度不是同一个目标函数。给定预算 B 后，应联合选择信号、到达路径、CU、优先费、tip 与发送时序，最大化首买概率；金额的全网固定分成无法替代这种选择。

本文把“双触发 + 路径定向竞价”列为工程推荐，未证明其在所有网络状态下优于单一触发。现成 bot 仅在能提供所需触发、费用与去重控制时适合采用；品牌名称或“首区块”宣传不构成速度排名。

## 5 可执行的参数规则与起测档

推荐原则：先保证完整买单有效、尽早抵达可执行位置，再在已确认路径内竞价。下面给出可直接实现的选择规则。数值档是便于复现的研究配置，没有测得其首买胜率或实际清算价；不能将“热门开盘一律 0.01 + 0.1 SOL”写成最优结论。

| 项目 | 选择规则 | 本节演示值 |
| --- | --- | --- |
| 交易格式与 CU | 用 legacy/v0 演示。L = 向上取整（完整成功路径 CU × 1.10）；覆盖账户创建、保护和 tip。 | 若已验证完整成功路径 ≤180,000 CU，则 L = 200,000。 |
| gas / 优先费 | 按目标可写账户或完整交易取费用估算，选择高竞争档；先核对返回单位，再换算 CU 单价并设单次上限。 | P = 0.01 SOL；c = 50,000,000 micro-lamports/CU。 |
| Sender Max tip | 先满足 0.001 SOL 门槛；在同类开盘、同路径下比较 tip 档和到达延迟，首发前选档。 | T = 0.1 SOL 是预算演示；不是实时推荐价或清算价。 |
| 频率与退出 | 使用确认可用的 Sender 50 TPS 额度：常规重发 40 req/s，预留额度给即时创建信号等请求。 | 25ms 间隔；最多 20 笔独立交易可落链；获知成交或他人先买即停止新发送。 |
| 请求选项 | 成功路径已验证后，可用 base64、skipPreflight=true、maxRetries=0；由本地调度重发。 | 复用已预热连接；blockhash 未过期；以真实 API 额度限流。 |

资料：[1][2][5][6][15]。Sender 的 50 TPS 是文档标准额度，不代表本研究持有 key 或已验证该账户额度。每个区域、连接和服务的实际限制均须遵守，不能把多端点数量当作可任意叠加的配额。遇 429 先纠正限流。Jito 普通默认入口为每 IP、每区域 1 req/s，不能照搬此 25ms 档。[3]

**演示预算**

若只需 1 个签名、每次 P = 0.01 SOL，且共享保护保证至多一次成功，20 笔全部落链时的原生费上界为 20 × 0.010005 = 0.2001 SOL；加一次 0.1 SOL tip，共 0.3001 SOL，另计买入本金、协议费用和账户租金。共享保护须真实实现；本论文不提供已部署的保护程序。

## 5.1 提前多久、多久发一次

只有 mint，没有可靠开盘时间：预构建后等待最早有效创建信号，收到即发，额外人为等待设为 0ms；依 25ms 档短窗重发。不要把“提前 1 秒盲发”视为最优。普通交易没有等待 mint 出现后再执行的通用挂单语义，过早执行会失败；bundle 也可能在模拟阶段被拒绝。[3][8][9]

已有可信的链上开放门槛 T0：先估计目标路径的有效单程处理延迟 d50、d95，及链上时钟映射误差 ε。这不是简单将 HTTP RTT 除以 2；还包括发送商排队、转发和执行资格。按时间门槛、slot 门槛分别校准，不以网页倒计时或整数秒 blockTime 反推毫秒级 T0。

Δ = 25ms；k = ceil(max(0, d95 + ε - d50) / Δ)

t(i) = T0 - d50 + (i - k) × Δ，i = 0, 1, 2, …

这是使一个发包点接近 T0、并向前覆盖延迟不确定性的工程起测网格，不是由竞价规则推导出的唯一最优解。重发至 T0 + 200ms、达到次数/费用上限或收到退出信号，以先到者为准。创建信号到来即使用预留额度触发，不等待下一个网格点。

| 假设输入（本研究未实测） | 对应操作 |
| --- | --- |
| d50=10ms；d95=20ms；ε=5ms | k=1，第一次在 T0-35ms，第二次在 T0-10ms。 |
| 随后每 25ms；至 T0+200ms | 后续为 +15、+40、+65、+90、+115、+140、+165、+190ms，共 10 个计划请求。 |
| 发送方式与失败限制 | 可优先重投同一签名；改变费用、blockhash 或收款人才需重新签名。事件触发请求也计入限流与次数预算。 |

**同一签名重发的边界**

重复同一签名有助于多次送达，不能保证“早期已执行失败后，稍后再成功”。签名已在规范链落为失败后，再投同一签名不会变成一笔新的可执行买单。若改用独立签名重试，各笔可能分别扣费；必须共享一次性保护。停止发送也不能取消已在途的交易，若没有可靠首买条件，晚到成功仍会支付 tip。

上线前替换假设：若未取得有效路径延迟分布，先采用事件触发；35ms、25ms 和 200ms 仅用于这份演示。模拟成功与额度允许是前提，不能用“发得越密一定越好”替代同条件对照。

## 高预算：从 0.1 SOL 改为 50 SOL

若单次 tip 预算确为 50 SOL，演示交易可保持 L=200,000、P=0.01 SOL，仅将同笔 tip T 改为 50 SOL。最多 20 笔独立尝试均落链、且仅一次成功时，原生费加 tip 上界为 50.2001 SOL，另计本金及协议费用。它是你愿意实际支付的高预算档，不是该机会的最优费率证据。

**什么时候 50 SOL 仍然会花错**

同笔交易失败时 tip 回滚，但原生费保留；成功排第二也会支付全部 50 SOL。除非目标状态提供可验证的“此前无人买入”条件并被同笔检查，否则一次性保护只保证自己最多买一次。不要把 50 SOL tip 单独放在另一笔无条件付款交易。

调整顺序：先检查信号到达、有效路由和成功路径；确认属于同窗口费用竞争后，再增加该路径认可的费用。原生路径重视优先费，传统 Jito bundle 看 tip/CU，BAM/DBI 看总费用/CU，Sender 还包含服务侧队列。[1][3][4][5] 没有对所有路径都最优的固定 gas/tip 比例。

## 5.3 把“最优”落实为预算与执行决策

对“尽可能第一”的目标，先选可执行集合：成功 CU、可用路径、真实额度、最大总费用及保护条件都满足，才比较报价。没有记录到达分布与对手竞争时，不能从单笔案例计算最优 tip；可优化的是参数规则、预算一致性和触发后的工作量。

## 先锁预算，再锁首发档

Tcap = B - N ×（基础费上限 + Pcap）- 协议费用预留

B 为此次事件允许的链上费用总额，不含买入本金和可退租金；N 是可能独立落链并扣费的交易数。若 B=50 SOL、N=20、单签名且 Pcap=0.01 SOL，则 Tcap=49.7999 SOL，再减协议费用预留。因此“总预算 50 SOL”和“tip 给 50 SOL”不是同一个设置。

先按完整交易 / 可写账户取得当前报价及单位，再计算原生优先费并检查上限；tip 也须同时满足服务门槛与 Tcap。若所选档超预算，必须减少次数、改变费用档或放弃该档，不能静默截断后仍声称执行了原方案。首发前选好档位；错过首买后再逐级加价，无法补回已发生的顺序。

| 开盘前固定的内容 | 触发时只做必要动作 |
| --- | --- |
| 程序、池账户分支、买入金额、最大支出 / 最低输出、CU、保护逻辑 | 验证最早事件来自目标程序与 mint；仅补齐创建消息中此前未知的字段，避免临时查询费用 API。 |
| 主路径及可用配额；从官方列表预选一个 tip 账户；每条付款规则 | 使用已预热入口立即送出；不要在触发后才查询收款账户。其他服务是否认可该笔 tip 必须事先确认。 |
| 有效 blockhash 及到期判定；所有独立版本的预算与共享保护 | 检查有效性后签名/发送；重投同一签名只算送达重试，已落链失败后需新消息 / 新签名才能重新执行。 |

**消息版本必须与成功 CU 一起冻结**

若用 Memo 或其他字段生成有限的独立消息版本，它们也必须纳入完整成功路径的 CU 评估。新增账户、保护指令或 tip 转账后，不能继续套用旧模拟的 CU。多服务版本即使只改收款人也可能分别执行；不要把多个未互认的 tip 都塞进同一成功买单。

费用目标与停止规则：这套决策只争取更高首买概率，不能同时保证净利润最高。已有他人首买的可靠信号时停止新发；已在途的版本仍可能成功并支付 tip。没有可验证的首买条件时，必须把这个后续成交费用计入方案。

## 7 失败成本、验证与最终建议

沿用演示值 L=200,000、P=0.01 SOL、T=50 SOL。费用计算适用于 legacy/v0，不包括本金、协议费用和租金：[1][9]

| 结果 | 同笔 tip | 原生费用 |
| --- | --- | --- |
| 成功且第一 | 支付 50 SOL | P + 基础费 |
| 成功但排第二或以后 | 仍支付 50 SOL | P + 基础费 |
| 上链执行失败 | 回滚，不支付 | 仍按请求 CU 收 P + 基础费 |
| 仅被接口接收、最终未落链 | 未执行转账 | 不产生该笔规范链交易费 |

若仅消耗 20,000 CU 即失败，仍按请求的 200,000 CU 收取 0.01 SOL 优先费。100 笔独立失败交易全部落链，优先费合计 1 SOL。以太坊常规 gas 按实际计费 gasUsed 结算，二者不能直接等同。[12]

## 7.1 怎样把起测档变成有依据的最优参数

在相同场景、同预算口径下，分别比较事件触发与预发送，25/50/100ms 间隔，以及 0.01/0.1/1 SOL 等 tip 档；这些档位是实验候选，不是三个推荐市场报价。原生优先费同时按账户竞争更新。记录客户端单调时间、源事件、每次发包、入口回应、重签原因、规范链排名和所有失败费；并保留 leader、路径与程序版本。

主要指标为外部首买率，附置信区间、样本量、费用分布及前五笔率。不同方案同时争同一 mint 会互相干扰，应在可比较开盘间轮换；仍须披露目标差异。主网案例只能支持其实际读数，不能给出发包提前量和频率；本文这些字段保持未知，未做真实抢买试验。

**本论文给出的操作结论**

未知开盘时间：预构建、最早创建信号到达即发；已知 T0：按测得路径延迟布置短窗网格。成功 CU 加约 10%，按路径分配优先费和 tip，付给官方指定的一个账户。示例为 200,000 CU、0.01 SOL 优先费、0.1 SOL tip、25ms 重发；符合假设时的定时样例从 T0-35ms 开始。这是可执行的起测档；当前没有证据将它称为所有 Solana 开盘的最优固定设置。
